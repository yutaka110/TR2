## 2. 進捗の更新ルール

状態は次のいずれかにする。

| 状態 | 意味 |
|---|---|
| 未着手 | その作業の実装・調査をまだ始めていない |
| 作業中 | 調査、設計、実装を進めている |
| 検証待ち | 成果物はできたが、完了条件の確認が残っている |
| 完了 | 表にある完了条件を満たし、ログや成果物を示せる |
| 阻害要因あり | 次へ進めない具体的な理由がある。原因と解除条件を記録する |

コードを追加しただけなら「検証待ち」とし、ビルド・必要な動作確認を経て「完了」にする。計画やドキュメント作成の作業は、内容と参照の確認をもって完了にできる。

今後のReach-RT作業では次の区切りで更新する。

1. **開始時**：対象ID、着手状態、今回の範囲を更新する。
2. **意味のある区切り**：実装・検証・問題発見の結果を短く報告する。長い作業では途中経過も伝える。
3. **終了時**：現在地、タスク状態、確認結果、未解決点、次の一手を更新し、作業ログに追記する。
4. **仕様変更時**：変更理由と影響するIDを記録する。研究範囲の変更は仕様書にも反映する。
5. **再開時**：このファイルと最新作業ログを読み、git差分と必要な証拠を確認する。以前の検証が別のコード状態に対するものなら、そのまま現在の合格証拠にしない。

作業ログは履歴として追記し、このファイルは最新状態に保つ。会話だけに完了情報を残さない。実装の完成と、H1～H4の仮説が支持されたことは別々に管理する。定期監視や自動実行を設定したという意味ではなく、実際に作業した区切りで更新する運用である。

### 毎回の報告形式（ユーザー指定）

以後の作業報告は、会話と資料の双方で次の順に揃える。最終報告だけで現在地と次工程を理解できるようにし、コード名や専門用語の列挙で説明を済ませない。

1. **現在地**：対象のG番号・タスクID、完了/作業中/未着手、今できることと残ること。項目数と研究ゲートの通過を区別し、項目数を工数の進捗率に換算しない。
2. **今回実装したものと目的**：解決する問題、入力→処理→出力、利用場面で変わる動作を平易に説明する。専門用語は初出時に意味を添え、必要なら変更前後の具体例を示す。研究における役割と前提条件も述べる。
3. **検証結果と限界**：実行条件、確認した挙動、結果、証拠へのリンク、未確認事項を示す。実装の動作確認と研究上の有効性を区別する。
4. **次工程**：次のタスクID、実装内容、その工程を行う理由、完了と判断する条件を明記する。予定を実施済みとして書かない。

実装を伴う区切りでは、そのまま面談・技術レビューで使える短い説明文も実装説明書へ残す。着手時・途中・終了時で、計画、進捗、検証結果を矛盾させない。

直近の次工程は**G1-04：受信画像によるマーカー検出・姿勢推定・固定制御器**。復号画素から既知マーカーを見つけ、目標に対する距離・向きを推定し、前進/旋回/停止指令を生成する。ロボットの真の座標を制御器へ渡さず、未検出・曖昧な推定・古い観測を扱えることを確認して完了とする。逆方向の指令UDPと通信断時の制動はG1-05、実映像によるT1/T2の18初期姿勢での作業成功確認はG1-06の完了条件である。

```text
G0 条件確認・既存版の基準記録       完了
 ↓
G1 理想回線で映像による閉ループ制御を成立させる ← G1-01～03完了、次はG1-04

G2 回線制約・復号状態・通信量を正確に観測する
 ↓
G3 強い比較方式と小規模モデルを作る
 ↓
G4 Reach-RTを実装し、予備実験で調整する
 ↓
G5 条件を固定して確認実験を行う
 ↓
G6 実測比較画面・配布物・研究報告を完成させる
```

デバッグ用の映像・数値表示とログ保存はG1から用意する。G6まで可視化を後回しにする意味ではない。G6では見やすい比較再生と成果物としての仕上げを行う。文献調査と小規模の理論検討は基盤開発中にも進められるが、ゲート完了にはそれぞれの証拠が必要である。
