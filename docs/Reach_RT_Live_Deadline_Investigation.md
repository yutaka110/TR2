# ライブ実行の撮影期限超過：原因調査

2026-09-25。対象は23:25の実行セッション `090E4BD8-032E-4AAD-BCB7-2F89AE92A7DC`。

## 原因

Visual Studioで起動した実行ファイルは `generated/outputs/Development/GE3.exe` だった。前回E029の仮想カメラ高速化はDebugにだけ適用されており、Developmentではプロジェクト全体の最適化無効設定を継承していた。実際のコンパイル履歴にも、`ReachRobotWorld.cpp` に `/Od` が指定されている。前回のDebug試験だけでは、この構成差を検出できていなかった。

画像生成処理は、床・壁の画素計算と、マーカーの各画素に占める面積の計算をCPUで行う。接近してマーカーが大きくなるほど面積計算の対象画素が増える構造である。今回のログでも時間の経過とともに画像生成時間が増えた。

| 実行ログから確認した項目 | 値 |
|---|---|
| 撮影予定の間隔 | 33.333 ms（30 Hz） |
| 最初の30画像の生成時間中央値 | 7.556 ms |
| 最後の30画像の生成時間中央値 | 32.740 ms |
| 画像生成時間の最大値 | 35.845 ms |
| 生成だけで33.333 msを超えた画像 | 11枚 |
| 撮影予定が2回分に積み上がった時刻 | 実験時計の開始から約8.170秒 |
| 実際に生成した画像 | 243枚 |

生成に加えて待機・制御などの処理時間も必要なので、生成だけで周期を使い切ると遅れが蓄積する。`camera.Poll()`が2回分の予定を返し、`cameras > 1` の検査が停止させた。過去のロボット姿勢に対応する画像を現在の姿勢から作り直すことはできないため、これは計測の整合性を守るための停止である。セッション全体の8.900秒という終了記録には、実験時計開始前の準備と失敗後の終了処理も含まれる。

撮影キューの最大深さは1、復号失敗・画像識別不一致は0。通信側には欠落や鮮度棄却の記録もあるが、今回の例外を直接起こしたのは撮影予定の取りこぼしである。デバッガーやOSのスケジューリングが上乗せした時間までは、このログだけでは分離できない。

## 修正と意図

`GE3.vcxproj`の`ReachRobotWorld.cpp`に対する速度最適化を、DebugとDevelopmentの両方に適用した。Developmentの他のモジュールの最適化設定、画像生成式、30 Hzの周期、計測を無効化する検査は変更していない。

説明例：「Development構成で仮想カメラの最適化が抜けていました。画像生成が撮影周期を超え、過去画像を捏造しないための検査で停止していました。構成間の設定差を修正し、同じDevelopment構成の実画面で再検証しました。」

## 検証

隔離したDevelopment x64ビルドが成功し、コンパイル履歴で対象ファイルの `/O2` を確認した。実際の研究画面を表示して20秒×2回を実行し、各回で物理2,000／撮影600／制御400刻みを完了、ロボット移動・復号・通常画面への復帰を確認した。画像生成の中央値は各6.775 ms・6.749 ms、最大19.271 ms・32.425 msだった。

同じPIDで通常→研究→通常→研究→通常を完了した。ビルド時ソース一覧と実行ファイルのハッシュを照合した。今回の検証はVisual Studioデバッガーを接続していない。デバッガー接続中の時間保証や全初期姿勢の再認定ではなく、ブレークポイント停止・他負荷等でも期限超過は起こり得る。

元の失敗セッションは保持した。[原因の集計](../artifacts/reach_live_development_20260925/verification/user_failure_analysis.json)、[画面切替試験](../artifacts/reach_live_development_20260925/verification/navigation_01/report.json)、[修正後の照合・撮影時間](../artifacts/reach_live_development_20260925/verification/fix_audit.json)。同じディレクトリに修正前後のコンパイル指定を保存した。

通常のVisual Studio出力exeは上書きしていない。実行中ならShift+F5で停止し、Development構成のままCtrl+Shift+Bで再ビルド、F5で起動して「Research Live - T2」を押す。
