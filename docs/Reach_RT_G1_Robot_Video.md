# Reach-RT G1-02 / G1-03 実装説明

更新日：2026-09-21。対象は仮想ロボット・実映像経路・撮影情報の対応付けである。画像認識による自動制御、逆方向の指令UDP、研究方式の優位性評価は次の段階で行う。

**後続実装**：現在は[G1-04の画像認識・制御](Reach_RT_G1_Visual_Control.md)まで完了。以下はG1-02/03時点の実装・証拠である。標準起動cmdはG1-04へ進め、旧接続確認は`open_reach_g1_robot.cmd`に残した。G1-04の版では、同じ寸法のマーカーを画素の被覆面積で描くように改良しており、旧バイナリと画素生成版が異なる。

## 1. 対外説明に使える要約

> PC上に低速ロボットと作業空間を作り、ロボットに固定した仮想カメラの画素を、実際のH.264・独自UDPプロトコル・復号器に通す基盤を実装しました。コーデックは入力と出力のタイミングが一致しないため、出力PTSをキーに元の撮影ID・撮影時刻を引き直します。さらに画像に埋め込んだ番号を復号後に読み取り、メタデータだけが一致している状態を合格にしません。現在は時間で決めた前進・停止指令による接続検証までです。受信画像から指令を生成する閉ループと、通信方式の比較はこれから実装します。

本体はC++である。Pythonは実行条件の作成・起動・記録・検証を担当し、物理計算、画像生成、符号化、送受信、復号には使っていない。

## 2. 何を、どの意図で実装したか

| 部品 | 実装内容 | 意図 |
|---|---|---|
| [RobotWorld](../research/ReachRobotWorld.h) | T1通路/T2開いた床、100 Hzの運動、加減速、接触・場外・成功保持・期限判定 | 通信に依存しない作業環境と評価基準を固定する |
| 仮想カメラ | 床・壁・既知マーカーを透視投影し、640×360のNV12画素を生成 | 真値の座標を画像推定の代用にしない |
| [RobotVideo](../research/ReachRobotVideo.cpp) | 実H.264→RNVP v3→localhost UDP→既存の復号ワーカー | 既存エンジンの実処理と待ち時間を含めて測る |
| [FrameIdentityLedger](../network/FrameIdentityLedger.h) | 受理された入力PTSと撮影情報の台帳。出力PTSで一度だけ取り出す | 遅延出力・順不同出力を現在入力に誤帰属しない |
| 画像番号照合 | 画像内のframe ID・stream ID・CRCを復号画素から読み取る | PTS照合とは独立して、画像内容との一致を確認する |
| 参照状態の破棄 | 研究経路で欠番を検出したらflushし、台帳を消去。IDRまで待機 | 参照画像が失われたP画像を正常な観測にしない |
| 復号前のFIFO | 研究経路では最大32 AUを順番に保持。受信/復号スレッドの取り出しを直列化 | バースト出力の途中のP画像を「最新だけ残す」処理で失わない |
| UDP受信待機 | selectで到着を待ち、recvfrom自体はタイムアウトさせない。研究経路の受信バッファは4 MiB | 到着待ちと受信を分離し、無損失設定の欠番を解消・監査する |
| 終了時の排出 | 撮影停止後、encoder出力、UDP到着、decoder出力の順で排出 | 内部バッファに残る最後の画像も検証対象にする |
| 基盤画面 | 受信画像、観測用の真値マップ、枚数、照合結果、撮影→復号時間 | 見えているものと測定しているものを説明可能にする |

画像生成はCPUによる簡易描画、画面はWin32/GDI、コーデックはMedia Foundationである。この段階ではDirectX 12による工場表現の作り込みは行っていない。

## 3. 前提・条件・入力境界

- １台のWindows PC、同一の単調時計。映像UDPは`127.0.0.1`の自動割当ポートに限定する。外部ネットワークへ送信しない。
- `robot_video`は物理100 Hz、撮影30 Hz、指令更新20 Hz、最大60秒。物理は10 ms刻みで最大5刻み追いつく。それ以上の遅れ、撮影周期を丸ごと取り逃がした実行、撮影キュー超過は無効として残す。
- 半径0.20 m、最高速度0.30 m/s、最高角速度0.8 rad/s、加速0.30 m/s²、制動0.60 m/s²、角加減速1.6 rad/s²。スリップなし。停止には制動時間が必要である。
- カメラは前方0.10 m、高さ0.35 m、水平FOV70度、歪みなし、640×360/30 Hz/1.5 Mbps。画素は白黒であり、色再現・照明頑健性の検証ではない。
- T1の壁はx=0～3 m、基準幅0.75 m、高さ0.8 m。T2は開いた床。既知マーカーは一辺0.24 m、内部4×4の非対称パターン`8B35`と黒枠を持つ。中心はT1でx=4.0 m、T2でx=2.8 m、y=0、高さ0.35 m。
- T1は中心x=3.20～3.35 mで停止、T2は(2.0, 0)から0.10 m以内・方位5度以内・速度0.02 m/s以下を１秒保持すると評価器が成功を記録する。接触・場外・60秒経過は失敗条件。これは評価器の実装であり、実映像による作業成功の証明ではない。
- 実行用設定は[robot JSON](../config/reach_rt_g1_robot.json)。初期y/yaw、通路幅、T1/T2、実行秒数、encoderのauto/softwareを指定する。その他のモデル定数はこの実装版で固定し、セッションの`world_model.json`とソースに記録する。全INITIAL項目を自由に変更できる設定実装ではない。
- `seed`は記録されるが、この段階の世界・移動指令には乱数を使わない。同じ初期条件・指令・刻み数なら軌跡が一致する。
- 既存のFEC、適応制御、pacing、ACK再送を研究試験では有効にしていない。容量制約や双方向回線のモデルはG2で導入する。

今回の指令源は`time_script_v1`で、12秒まで0.15 m/sの前進、以後0 m/s、角速度0である。指令は経過刻み数だけを参照する。目標位置やロボット真値を見て操縦する処理ではない。標準15秒実行は前進と制動の確認であり、T1/T2の自動完了を目的としない。

`RobotTruth`を使う箇所は世界更新・描画・評価ログ・観測用マップである。未来の画像制御器へ渡すAPIはまだ追加していない。G1-04では復号画素と受信側で利用可能な情報だけを入力にする。

## 4. G0の時刻誤対応をどう直したか

G0では、現在入力したAUより50 ms古い画像が返っていても、現在入力のframe ID・撮影時刻を付けていた。API呼出しの成功と、現在入力の画像が出力されたことは同義ではない。

```text
撮影ID / stream ID / capture_us
    → encoder受理時に入力PTS= capture_us × 10 を登録
    → encoder出力PTSで撮影情報を検索
    → RNVP v3に元の撮影情報を格納してUDP送信
    → decoder受理時にAUのPTSと撮影情報を登録
    → decoder出力PTSで元の撮影情報を検索
    → 復号画素の番号・stream・CRCと撮影記録を照合
```

Media FoundationのPTS単位は100 ns、研究ログの時刻はµsである。入力の現在時刻で返却画像を上書きしない。各台帳は256件まで、二重入力・二重出力・対応なしを拒否する。stream変更、flush、再初期化時に古い台帳を破棄する。終了時のdrainは残った入力に対応する出力を回収してから台帳を消去する。

起動時の形式変更も修正した。非同期encoderの形式変更後は次の出力イベントを待つ。decoderはMFTが提示する実際の出力形式を使い、NV12の格納高と表示高を分ける。形式通知だけで画像がない返却を、識別不能な画像と混同しない。

画像番号の検証領域は先頭40行、frame ID 32 bit・stream ID 32 bit・識別子16 bit・CRC16と反転行である。領域は診断用で、G1-04のマーカー検出対象から除外する。不一致画像は検証を失敗させ、画面の正常な受信画像には更新しない。この番号は暗号学的な認証でも、参照画素すべてが正しい証明でもない。

**欠落時の観察**：修正途中の試験では、frame 20を欠落させると、その後24枚の画像番号が読めないのに復号APIは成功した。これを合格にせず、研究経路の欠番検出・flush・IDR待機を追加した。完全なH.264参照DAGを解析した方式ではなく、今回の連続frame IDの送信条件に対する保守的な扱いである。参照世代・期限・再同期の詳細な研究評価はG2-04で行う。

既存モードにもdecoder出力PTSに基づく対応付けと形式処理の修正は適用する。ただし、既存sender全経路の撮影PTS対応を今回の研究試験で保証したわけではない。撮影画素からの一貫した照合の合格範囲は新しい`robot_video`経路である。

Release x64ビルド成功。最終exe SHA-256は`c1a7a3f9fc28f1cd90a172601ea9661eed6693ebcb1795c6f352100a43db66d3`。途中で失敗したrunも削除せず、修正後の結果と区別して保存した。

| auto、T1、15秒 | 450 / 450 | 前進、12秒からの制動、終了までの映像接続 |

- 基盤の単体663チェック、実アプリの設定・分岐・セッション分離12ケースを同じ変更状態で再検証した。

## 6. 起動と記録の読み方

通常は[起動用cmd](../tools/open_reach_g1.cmd)をダブルクリックする。標準15秒の接続確認後、結果画面は閉じるまで残る。[専用cmd](../tools/open_reach_g1_robot.cmd)も同じ研究段階を起動する。保存先は横スクロール可能な読み取り専用欄に変更し、長いパスを選択・コピーできるようにした。

```powershell
# ビルド
powershell -NoProfile -ExecutionPolicy Bypass -File tools/build_reach_g0.ps1 -Configuration Release -OutputName reach_g1_robot_20260921

# 画面あり（nameは実行ごとに変える）
python tools/run_reach_g1.py --stage robot_video --name my_robot_01 --show

# ソフトウェアencoderで画面なし
python tools/run_reach_g1.py --stage robot_video --encoder software --task T2 --name my_software_01 --duration 4

# G1-01の時計のみを新しい実行ファイルで確認
python tools/run_reach_g1.py --stage foundation --build-name reach_g1_robot_20260921 --name my_foundation_01 --duration 2

# 実映像による受入試験
python tools/verify_reach_robot.py --name my_acceptance_01
```

起動単位のフォルダは`artifacts/reach_g1_robot_20260921/runs/<name>/`、研究セッションはその中の`sessions/<GUID>/`である。実行は起動単位の作業ディレクトリに分離し、既存のコーデック・RNVP診断ログもその`logs/`へ保存する。

| ファイル | 読み方 |
|---|---|
| `launch.json` / `manifest.json` | 実行引数、環境指定、exe/configのSHA-256、セッションID |
| `source.patch` / `source_hashes.json` / `research_source/` | 未コミット差分、ソース一覧のハッシュ、research/network/configのスナップショット |
| `config.input.json` / `config.effective.json` / `world_model.json` | 指定条件、検査後の条件、固定モデル |
| `world.csv` | 物理刻みごとの位置・速度・接触・成功/失敗判定。自動制御の成果とは扱わない |
| `captures.csv` / `encoded.csv` | 撮影ID/時刻、encoder出力PTS、実IDR、drain、意図的欠落 |
| `decoded_audit.csv` | 復号画像の番号、元の撮影時刻、出力PTS、一致/重複、撮影→復号時間 |
| `robot_video_summary.json` | 撮影/符号化/送信/復号/照合枚数、drain枚数、失敗と欠落条件 |
| `summary.json` | 試行全体の完走・中断・無効。`task_result=not_run`、`closed_loop_validated=false`を維持 |
| `last_received.bmp` | 最後に照合を通った受信画素。画面全体のスクリーンショットではない |

`robot_video_completed`は接続・照合試験の完走を意味する。画面の枚数は復号監査の集計で、画面提示FPSや作業成功率ではない。表示用キューで期限を超えた画像の破棄が別に計上されるため、`freshness_drops`を画像ID不一致の件数と混同しない。撮影→復号時間には実際のバッファ待ちが含まれ、複数PC間の時計同期精度を示すものではない。
