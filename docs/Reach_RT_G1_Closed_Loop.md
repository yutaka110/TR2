## 検証の目的と条件

G1は「画像から判断した指令を通信経由でロボットへ戻し、作業を完了できる実験基盤」の確認段階である。Reach-RTの送信方式が比較方式より優れるかを測る段階ではない。

G0で指定した18初期姿勢を変更せず使う。T1は y = −0.05 / 0 / +0.05 m と yaw = −5 / 0 / +5度の直積9条件。T2は y = −0.15 / 0 / +0.15 m と yaw = −10 / 0 / +10度の直積9条件。全て x = 0、初速・初期角速度は0。T1通路幅0.75 m、ロボット半径0.20 m。

各条件の観測窓は60秒。成功後も撮影・通信・制御の記録を続ける。物理100 Hz・撮影30 Hz・制御20 Hzで、正常完走なら6,000物理刻み・1,800撮影画像・1,200指令になる。seed=101、同一PCのloopback UDP、意図的損失なし、encoder=auto。実際にハードウェアが選ばれたかは試行ごとに保存する。既知マーカー・較正済みカメラ・平面運動・スリップなしという前提である。

T1の成功は接触・場外なしで中心 x = 3.20～3.35 m、速度0.02 m/s以下を1秒保持。T2は接触・場外なしで目標(2,0)から0.10 m以内、yaw±5度以内、速度0.02 m/s以下を1秒保持。60秒までに成立しなければ未達。周期遅れ・待ち行列超過・映像照合失敗等で観測窓を満たせなければ無効試行として区別する。

## 実装したものと意図

実験本体は引き続きC++。Pythonの[検証器](../tools/verify_reach_closed_loop.py)は、条件の指定・実行・保存済み記録の監査を担当する。Pythonから真の位置を制御器へ渡す経路はない。

1. 実行前に18条件・60秒窓・exeハッシュ・検証器ハッシュを `plan.json` へ保存する。試行を選び直したり、成功するまで自動再試行したりしない。
2. 仮想カメラ → 実H.264符号化 → RNVP/UDP → 復号 → 受信画素からの姿勢推定 → 共通制御器 → RCMD指令UDP → 受信側検査 → 所定の加減速、という経路で動かす。
3. [指令監査器](../tools/verify_reach_command.py)で実際の電文CRC・値・根拠画像・受信時刻・期限・実適用を照合する。新しい判定器は、初期姿勢から受信指令による加減速と運動を独立に再計算し、世界ログと一致するか検査する。
4. 目標条件と1秒保持を独立に再計算する。成功時に世界が速度をゼロへ固定するため、その行は固定前の速度を再計算して使う。成功後の固定された世界を使って保持条件を後付けで満たしたことにはしない。
5. 60秒の全周期数と1,800画像の照合、1,200指令の受信、接触・場外、成功後の状態維持を確認する。各条件の結果を逐次 `report.json` に保存する。全18件が有効かつ成功した場合に限り、この行列の `passed` をtrueにする。

真値は評価と描画だけに使う。制御器には受信画像由来の推定・既知の地形と目標・過去の画像情報だけを入力する。アプリの `command_udp_completed` は観測窓の終了を示す。基盤の `summary.json` に残る `task_result:not_run` / `closed_loop_validated:false` は旧基盤の予約フィールドであり、今回の判定源は外部の `verification/.../report.json` と監査済み世界ログである。単一試行の終了だけでG1全体を合格にしない。

## 予備検証で見つけた問題

- 旧G1-05バイナリでT1中央を60秒実行したところ、x=3.17476092471 mで停止し、時間切れになった。1,800画像の照合と1,200指令受信は成立した。目標の8 cm手前でALIGNへ移る設定が、出口領域の下限3.20 mと整合していなかった。証拠：`artifacts/reach_g1_command_20260921/runs/g106_baseline_t1/`。
- 共通制御器v2ではT1のALIGN開始を目標まで2.5 cm、解除を4 cmに変更した。T2は従来の8/10 cmを維持する。目標領域・制動性能・成功判定は変えていない。T1出口手前で前進が継続すること、保持・復帰・ヒステリシスを単体検査へ追加した。
- `matrix_01` のT1(y=−0.05 m、yaw=−5度)では、壁余裕による停止が持続した。推定誤差・画像年齢・制動中の横移動を差し引いたうえで、さらに5 cmを要求すると、停止したまま条件を改善できない。約56.53秒で試験を中断し、途中CSVと計画・中断理由を保存した。この試行を60秒完走や成功に数えない。
- 壁余裕の追加分を全T1条件共通で5 cmから2 cmへ変更した。推定誤差・画像年齢・制動距離を差し引く計算は維持する。これはINITIAL制御設定の変更であり、実機安全保証ではない。G0の初期案と差があることをここに記録する。
- `matrix_02` の同じ初期姿勢では、約13.47秒時点で撮影キュー上限8枚を超え、試行が無効になった。古い画像を新しいものとして扱ったり、キュー上限・実時間条件を緩めたりはしていない。壁余裕停止も残っており、この変更だけで18条件の成立を保証しない。

### 固定版の検証で確認した課題

`matrix_03` は同じexe・設定で18条件を事前指定し、自動再試行なしで実行する。T1中央・yaw−5度の試行では18.19秒に世界ログ上の成功を記録したが、35.04秒の物理更新までで撮影キューが上限に達した。実時間窓を完走していないため合格に数えない。エンコーダ出力間隔の最大は923.034 ms、描画時間の最大は21.228 msだった。終了処理付近には約704秒の大きな時刻差も残る。現ログだけではOS/電源状態・MFT/ドライバ・スレッド待ちのどれが原因かを確定できず、「描画が重いだけ」と断定しない。詳細は `invalid_timing_diagnostics.json`。

T1中央・yaw+5度のframe 37では、採用した画像推定の位置誤差が0.122809 mとなり、記録した余裕0.100986 mを超えた。その画像を使うsequence 26では `wall_margin_stop` により前進指令は0だった。接触は起きていないが、初期の誤差余裕モデルが全観測を覆うとは言えない。該当画像・指令・評価真値は `allowance_violation_detail.json`、全条件の集計は `evidence_audit.json` に保存する。真値で制御出力を補正した結果ではない。

## 専門の場での説明例

「実際に圧縮・UDP伝送した受信画像からロボットの姿勢を推定し、その画像に対応した期限付き指令を逆方向UDPで返します。18種類の初期位置・向きを事前指定し、各60秒の記録を残します。アプリの成功表示だけに依存せず、保存した受信指令から運動と目標保持を別のプログラムで再計算します。目標に届かなかった試行と、処理遅れで測定条件が崩れた試行を分けることで、制御設計と実時間処理のどちらに課題があるかを説明できます。」

## G1全体の判定と次工程

同じexeで[G1-05の7ケース](../artifacts/reach_g1_closed_loop_20260921/verification/command_regression_01/report.json)も再検査し、正常・重複・並べ替え・遅着・通信断・復帰・不正電文の全てが合格した。0.30 m/sから0.60 m/s²で0.50秒・0.075 mの制動を維持した。この追加試験は18姿勢行列の分母には含めない。

**G1-01～05は完了を維持するが、G1-06は完了条件未達。G1ゲートは未合格（保留）とする。** 18姿勢の検証作業を実施したことと、18姿勢で有効な成功証拠が揃ったことを区別する。17件だけを分母にして「成功率100%」とは報告しない。再試行で無効試行を消したり、成功後の観測窓を短くしたりしていない。

次はG1-06の継続で、(1)エンコーダの入力受付・出力イベント・撮影キュー占有・スレッド待ち・終了処理の時間を計測し、キュー超過と終了遅延の原因を切り分ける、(2)遠方マーカーの誤差余裕と推定受理条件を再較正する、(3)全方式共通の修正を固定し、18条件を再度60秒ずつ検証する。無効・未達なしの18件と、較正範囲での誤差余裕の整合を確認してからG1を再判定する。

G1通過後の次段階は **G2-01：双方向の容量・直列化・有限キュー**。既知サイズの送信、送信中の容量変化、キュー溢れを期待値と照合する。今回はG2へ進めていない。現在はG1 5/6項目、全体12/38項目、研究ゲートG0のみ1/7である。
