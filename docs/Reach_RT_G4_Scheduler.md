# G4-03：ReachSchedulerと代替処理

更新：2026-09-25。前工程の[校正結果](Reach_RT_G4_Prediction.md)と[G4固定計画](Reach_RT_G4_Implementation_Plan.md)を入力とし、過去の証拠・計画は書き換えない。

## 実装の意図

通信に使える量と判断に使える時間の両方に上限を設け、予測が使えない状況でも実行可能な操作へ戻せる送信制御を作る。到着済み通知、送信側のキュー、実際に符号化済みの画像を20 msごとに読み取り、候補を選ぶ。判断時点では未来の障害、受信側の真値、後から判明する作業結果を使わない。

G4-02の校正表は、別試行の全6事象でBrier誤差が改善しなかった。そのため、この段階では校正済み確率を最大化しない。未校正の「対象画像が200 ms以内に実際の指令へ使われる頻度」を、費用と合わせた実験用の優先順位にだけ使う。

`score = raw_target_image_command_probability − 0.1 × candidate_IP_bytes / 65536`

これは60秒の作業成功率でも、単独操作の因果効果でもない。学習時の固定循環規則から選択規則が変わっており、新しい方策の予測誤差・有効性は未確立である。参照回復・後続画像・作業完了の予測は前工程の成果として残すが、重複する事象を足し合わせて成功確率に見せることはしない。G4-04で、この保守的な接続を対照とともに評価する。

## 構造と責務

| 部品 | 実装内容・責任 |
|---|---|
| `ReachScheduler.h` | 有限候補の順位付け、支持不足の判定、代替順序、周期番号の計算。通信や真値への参照を持たない |
| `ReachPrediction.h` | 最大16,000経路から最大64近傍を抽出。64行ごと・並べ替え前後・終了時に計算打切りを確認。中断時は部分的な確率を返さない |
| `ReachActionExecution` | 専用スレッド、高精度待機タイマー、因果的スナップショット、選択後の再検査、実行記録 |
| `NetworkManager::SendResearchRepair` | 遅延実行時に実送信キャッシュを引き直す。既存の完了ACK・再送TTL検査と送信直前の共通予算を通す |
| `RobotVideo` | 実H.264出力を保管し、スケジューラの開始・終了を実験窓と同期。IDR要求は次のエンコーダ入力で受理し、実出力と照合 |

各判断では、最新4画像それぞれにFRESH、PROTECT g2/g4/g8、REPAIRを生成し、共通のDEFERとREFRESHを加える。実装上は最大22候補で、仕様上限64以下。DEFERを常に残す。画像は最大786,432 byte、元の期限は撮影から200 ms、共通IP予算はG2の実sendto直前の計上を使う。FECは新規画像と実XORの組であり、架空のパリティだけを選ばない。

再送要求は、逆方向UDPで届いた欠落要求と実キャッシュ確認を起点に保留する。次の周期で選ばれた場合だけ再送を認可する。要求をまとめて未来の欠落情報を推測しない。IDR更新は要求予約とエンコーダへの発行、実際のIDR出力を分け、500 msの要求間隔と二重要求防止を維持する。IDR出力の送信費用は生成後の候補と実通信で払う。

## 期限・計算打切り・代替

候補集合に含まれる適格な映像・再送候補のうち、一つでも予測の支持が足りなければ、その判断全体を共通回復処理に切り替える。未支持候補を都合よく除いて、残った候補だけで最適と主張しない。支持条件は8近傍以上・2学習試行以上、通知の有効期間は250 ms。

代替の順序は、受信済み要求に基づく期限の近い再送、未処理のIDR要求、最新の未送信画像（g4が予算内ならFEC付き、そうでなければ通常送信）、DEFER。モデル未指定、通知失効、範囲外、計算打切りで同じ処理へ戻る。IDR要求は生成前で送信費用を確定できないため、成功予測による競争から分離し、共通回復処理として扱う。

計算予算は初期値5 ms。前回の選択結果を再利用せず、その周期の候補から代替を選ぶ。選択後にロックを取り直し、現在の参照世代、画像の存在、200 ms期限、再送回数、予算を再検査する。検査失敗または推論後のロック待ちで5 msを超えた場合はDEFER。実送信の直前にも期限・世代・予算を確認する。DEFER自体はロボットへの停止指令ではなく、指令が来なくなったときの停止は既存の指令受信器と制動モデルが担当する。

周期は実験開始時刻に対する20 ms刻み。Windowsの実行遅延で複数枠を逃した場合は、飛ばした枠数を記録し、古い判断を連続実行して追いつこうとしない。高精度待機タイマーの作成・待機失敗は実験エラーとして扱う。

p95≤2 ms・p99≤5 msは、このPC・この条件で検査する目標。5 msは協調的な打切りであり、OSの停止・ロック待ち・有界な後処理まで強制終了できる硬い時間保証ではない。判断時間にはスナップショット、探索、再検査、認可の記録を含める。RNVPへの投入は別時間として計測し、候補詳細CSVの整形・バッファへの追記はその後に行う。周期の開始遅れ、スキップ、5 ms超過も隠さず残す。

## 追跡できる証拠

- `scheduler.csv`：周期番号、予定・開始・スナップショット時刻、判断／投入時間、選択、代替理由、再検査結果、使用通知とfeedback番号。
- `scheduler_candidates.csv`：全候補の実画像・世代・期限・IP費用、16特徴、支持数、生の値と校正値、実際に使ったスコア。
- `scheduler_execution.csv`：周期→実行認可番号→IDR予約・発行。実行認可番号から既存の`action_wire.csv`、共通IP計上、復号、認識、指令、物理・作業結果へ追跡できる。
- 実行ごとのソース・exe・モデルのハッシュとコピー。学習・校正をこの検証データで再調整しない。
