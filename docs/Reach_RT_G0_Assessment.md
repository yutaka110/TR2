## 1. 結論と承認範囲

**G0の条件調査は完了。G1の基盤実装へ進める。研究性能の測定に使える状態ではない。**

実ビルド、生成映像のH.264/UDP loopback、正常・10%損失の各3試行、実コーデックの構文検査、復号出力の時刻監査を行った。既存エンジンを再利用する条件と、G1以降で解決する問題を特定した。G0の「完了」は問題がないという意味ではなく、ゲートに定めたビルド・基準動作・制約・初期タスク・比較方針を証拠付きで確定したという意味である。

特に、**復号出力と入力フレームの対応がずれている**。追加した時刻ログでは、記録された復号成功180件の全件で、出力PTSが現在の入力PTSより50 ms古かった。入力側のID・撮影時刻をそのまま出力画像に付ける現状の処理を研究用に流用できない。修正と検証はG1-03の必須条件にする。今回、この対応付け自体は修正していない。

## 2. 専門の場で説明する研究の意図

説明例：

> 圧縮映像を使う遠隔作業では、パケットが届いても、参照画像の欠損によって作業に使える画像にならない場合があります。また、同じ映像の遅れでも、通路中央を走っているときと停止位置に近づいたときでは影響が違います。Reach-RTでは、受信側の復号状態と画像から推定した作業状態を使い、再送・冗長化・新しい画像・IDR更新に通信量をどう配分するかを研究します。PC上の仮想ロボットでも、実際のH.264とUDPを通った画像から指令を生成し、作業成功率と使用通信量で評価します。現在は既存基盤の動作確認と測定上の問題の特定まで完了しており、改善効果は未検証です。

| 機能 | 実装する意図 | 判定できること | 現在の状態 |
|---|---|---|---|
| 仮想作業と実画素の送信 | 通信の劣化が作業結果に与える影響を閉ループで測る | 衝突、停止、期限内完了 | G1で新規実装 |
| 撮影から復号までのID・時刻対応 | 古い画像を新しい観測と誤認しない | 画像の年齢と指令の根拠 | 今回は問題を検出するログを実装 |

## 4. 実施した確認と結果

### 4.1 ビルド

通常の出力設定を変更せず、追加propsの明示importによって出力先を作業領域内の`artifacts/reach_g0_20260921`へ移した。基準版のRelease x64は警告28・エラー0。警告には依存コード/SDK由来のC4865がある。警告ゼロや別PCでの再現を達成したとはしない。

初回はビルド失敗。並列数を1にした再試行で、子プロセス環境の`Path`/`PATH`重複によるMSB6001が判明した。Pythonで環境名を正規化してMSBuildを起動すると成功した。マシンの環境変数は変更していない。失敗ログも`build_Release_attempt*`として保存した。

### 4.2 基準動作：正常と損失

カメラを無効化し、既存の生成映像を実H.264・ローカルUDPで送受信した。シナリオ名は既存実験器の`Baseline / QoE/Deadline Adaptive / Hybrid / FEC g4`と`10% loss / QoE/Deadline Adaptive / Hybrid / FEC g4`。各20秒、ウォームアップ5秒、seed 101/202/303、逐次実行。

| 条件 | 有効実行 | 表示fps：試行平均の平均 | 各試行平均の範囲 |
|---|---:|---:|---:|
| 正常 | 3 / 3 | 18.91 | 17.88～19.58 |
| 模擬10%損失 | 3 / 3 | 14.98 | 14.52～15.85 |

終了コード0、指定シナリオとの一致、復号ログを確認した。`network_summary`の計測区間は約14.01秒で、20秒全体の平均ではない。既存適応処理の動く基準試験であり、Reach-RTの640×360/30fps/1.5Mbps固定試験ではない。既存ログには480×270の復号、20fps相当のPTS刻み、符号化開始時7.25Mbpsの設定が現れる。

従来の遅延統計も保存したが、次節の時刻対応問題があるため撮影から表示までの正しい遅延として採用しない。表示fpsも作業成功率を意味しない。3試行から研究の優位性や統計的有意性を主張しない。seed固定でもOS/GPUの実行順まで一致するわけではない。

### 4.3 H.264出力の検査

既存`H264Encoder.cpp`を直接呼ぶ専用プローブを追加した。入力は640×360 NV12、30fps、目標1.5Mbps、90枚の移動模様。GOP30/Bなし/参照数1を要求し、入力番号45の直前にキーフレーム要求を出した。出力AUを個別保存し、Annex-B、SPSの一部、slice種別を検査した。

| 観測 | auto（Intel Quick Sync） | software |
|---|---|---|
| 出力AU / 入力失敗 | 90 / 0 | 90 / 0 |
| 検査範囲の構文エラー | 0 | 0 |
| 符号化寸法 | 640×360 | 640×360 |
| SPS profile / 最大参照数 | Baseline（66）/ 1 | Baseline（66）/ 1 |
| slice種別 | I 4 / P 86 / B 0 | I 4 / P 86 / B 0 |
| IDRの出力通番（0開始） | 0, 28, 45, 73 | 0, 30, 45, 75 |
| 最初の出力が得られた入力呼出番号 | 再確認runでは0 | 16 |

3組の実行でIDR通番と構文集計は一致した。最終的な再実行器の証拠は`codec_repro_check`にある。softwareでは最初の出力が約539 msまで遅れた。これは今回のプローブにおける立ち上がりの待ち時間であり、定常時の全フレーム遅延ではない。低遅延設定やBなしでも、バッファリングが消えるとは仮定できない。

IDR要求後に実IDRが現れることは観測できた。一方、エンコーダAPIが出力サンプルのPTSを公開していないため、出力通番45を「撮影番号45」や「要求から0 ms」と同一視しない。GOP30設定に対してautoの通常間隔は28だった。スケジューラは設定値からIDR発生を断定せず実NALを確認する。

**未検証**：PPSの参照設定、参照リスト変更、MMCO、長期参照、画像内容による正しさ、全入力と全出力のPTS対応。`max_num_ref_frames=1`だけで直前参照を証明しない。本解析器はH.264適合性検証器ではない。Media Foundationの設定と実出力を分ける方針は、[Microsoftのencoder仕様](https://learn.microsoft.com/en-us/windows/win32/medfound/h-264-video-encoder)と[decoder仕様](https://learn.microsoft.com/en-us/windows/win32/medfound/h-264-video-decoder)の各MFT仕様に沿って確認した。

初版プローブでは非同期`DrainOutput`のfalseを全てエラーとして数え、autoを失敗扱いにした。既存APIがイベント待ちタイムアウトでもfalseを返すため、入力/flush失敗と「イベントなしまたはエラー」を分離して修正した。後者がゼロだったとは報告しない。修正前の証拠も削除していない。

### 4.4 復号出力の時刻監査

`NetworkVideoReceiver`に、復号MFTの出力サンプルから取得したPTSと有効フラグを追加し、既存受信CSVに入力PTS/出力PTSを追記した。対応付けのロジックと回復方針は変更していない。

`pts_audit_auto`は正常回線・12秒で終了。記録対象の復号成功180件すべてで出力PTSが取得でき、`inputPtsUs × 10 − outputPts100ns = 500,000`、すなわち50 msの差があった。

例えば、入力PTS 100,000 µsに対して返った画像の出力PTSは500,000（100 ns単位）=50,000 µsだった。現行コードはこの出力に今回入力したフレームのID・撮影時刻を付けている。**「Decode呼出に渡したAU」と「その呼出で得られた画像」が一致する仮定は、この実行では成立しない。** ログは先頭フレーム等を抽出したもので、全フレームへの頻度の一般化はしない。

### 4.5 採用するコーデックモデルとG1/G2の合格条件

1. 実コーデックではIDR世代、同期済み/不確実/待機を保守的に管理する。欠損後にデコーダが画像を返しても、画素が正しい証拠にしない。
2. 単純な直前参照IP列は、小規模理論モデルの明示的仮定に限定する。実コーデックとの一致を証明したとは書かない。
3. G1-03で撮影ID・単調撮影時刻とencoder入力PTSを登録し、encoder出力PTS→AUメタデータ、decoder出力PTS→元の撮影メタデータへ照合する。現在入力を使った代入を廃止する。session変更、flush、再初期化、複数出力、欠落時に台帳を整理し、未対応出力は制御へ渡さず理由を記録する。
4. Bなしでもsoftwareのような遅延出力を含む試験を行い、入力の番号を画像にも描いて、PTS照合と画素側の番号の両方で確認する。正常、損失、並べ替え、IDR更新、再起動を検査する。修正後の鮮度・遅延ログでG1を判定する。
5. G2-04でIDR/Pの意図的欠損と再同期を実デコーダで検査する。既に消費した参照の後追い修復を実装が扱えない場合、その候補を実行不能にする。代わりにIDR更新を使う。
6. 初期バックエンドはautoで実際に選ばれたIntel Quick Syncを記録する。別PCや別ドライバへ移る際は同じ検査を再実行する。softwareへの切替を同じ実時間条件と見なさない。

### 5.2 B1～B3の具体的な初期実装方針

全方式で候補生成・ペーサ・IPバイト予算・認識器・制御器を共有する。候補は既存XORの群サイズ2/4/8/無保護、実際に存在する欠損パケットの再送、最新AU、新規IDR要求、待機。IDR要求には生成待ち・実際のサイズを含め、未生成IDRを送信済みにしない。候補上限64、周期20 ms、計画範囲200 msをINITIALとする。

| 方式 | 判断に使う情報 | 初期の評価目的 |
|---|---|---|
| B0 | 既存の回線・期限・回復統計 | 既存RNVPの固定設定。共通回線/計上/コーデック条件へ接続し直して測る |
| B1 | RTT、遅延分布、直近損失率と連続損失、AU長、欠損数、表示期限、予算 | 期限内に完全配送できるAUの期待価値 − 正規化した送信コスト |
| B2 | B1 + 到着済みの復号世代/同期状態通知 | 期限内に利用可能な復号画像になる期待価値と将来参照価値 − 送信コスト。作業特徴を入力しない |
| B3 | B1 + 到着済みの作業推定/観測年齢/停止余裕 | 作業上の期限内に役立つ配送の期待価値 − 送信コスト。復号依存は隠した配送モデルを使用 |
| R | B1 + 復号状態 + 作業状態 | 利用可能な画像が作業成立にもたらす予測価値 − 送信コスト |

B1は初期に`E[deadline-miss AU数] + λ × (IP bytes / 候補内最大bytes)`を最小化する有限候補計画とする。将来損失は見ず、過去の受信通知から独立損失/2状態の連続損失モデルを推定する。λは`0 / 0.1 / 0.3 / 1 / 3`を予備実験で比較し、同じ通信予算での作業成功を使って有利な設定を選んでから固定する。係数・窓長・モデル選択の候補数は全方式で記録し、提案だけ多く調整しない。

B2/B3/Rは同じ予測器の入力マスクとして実装し、隠す情報が共有キャッシュや特徴量経由で漏れないことをテストする。因果的に到着した通常NACK/PLIは共通で利用できるが、復号状態の拡張通知と画像由来の作業特徴は表の方式にのみ公開する。B3で復号状態を観測年齢等から間接的に推測できる可能性は記録し、「完全な情報分離」とは断言しない。

**比較の強さを満たす条件**：上記B1は独自の期限計画参照方式であり、Hairpin/Toothの再現ではない。G3では公開Hairpinモデルとの小規模一致確認に加え、フレーム長・損失集中度への適応を含む比較を調整する。RS等との能力差が結果を説明し得る場合は、同等のFECを全方式へ追加するか、結論をRNVP/XOR候補内に限定する。XOR比較だけで「最新手法を上回った」と主張しない。Tooth由来の特徴で独自学習した方式はTooth-inspiredと表示し、原論文の再現とは分ける。

新規性の候補は「復号状態と作業状態を同時に用いることによる判断の差と、その差が生じる条件」。組合せだけで新規性を保証せず、G3で反例・小規模厳密解・強い比較により研究を継続する根拠を確認する。

## 6. 実装に使う初期条件

機械可読な設計値は[reach_rt_initial.json](reach_rt_initial.json)に保存した。**設計専用であり、現アプリが読み込んで動く設定ではない。** G1-01で読み込み・範囲検査・manifest保存を実装する。すべてINITIALで、G5の固定値ではない。

### 6.1 世界とカメラ

世界座標はx前進/y左/z上、角度rad。ロボットは半径0.20 mの円、速度上限0.30 m/s、角速度0.8 rad/s。物理100 Hz、制御20 Hz、映像30fps。並進加速0.30 m/s²、制動0.60 m/s²、角加減速1.6 rad/s²。スリップなしの運動学モデルとし、摩擦係数から別の減速を重ねない。物理の遅れは最大5刻み追いつき、それを超えた実時間試行は無効理由を保存する。

カメラはロボット中心から前方0.10 m、高さ0.35 m、水平向き。640×360、水平FOV70度、歪みなし。内部パラメータはこの投影から計算して全方式に与える。これは較正済み単眼という限定条件であり、未知環境への適用は主張しない。

### 6.2 T1/T2とマーカー

| 項目 | T1：通路通過 | T2：位置合わせ |
|---|---|---|
| 地形 | 壁x=0～3m、幅0.75mを初期基準。0.65/0.90mも予備条件 | 開いた床、目標中心x=2.0m/y=0 |
| 初期姿勢 | x=0、y=−0.05/0/+0.05m、yaw=−5/0/+5度の9条件 | x=0、y=−0.15/0/+0.15m、yaw=−10/0/+10度の9条件 |
| 目標 | 中心x=3.25m/y=0、出口領域x=3.20～3.35m | 位置誤差0.10m以内、yaw誤差5度以内 |
| 可視マーカー | x=4.0m、y=0、中心高さ0.35m | x=2.8m、y=0、中心高さ0.35m |
| 成功 | ロボット全体が出口を通過、接触なし、速度0.02m/s以下を1秒維持 | 接触なし、位置/角度条件と速度0.02m/s以下を1秒維持 |
| 制限 | 60秒。失敗・成功後も通信量集計の観測窓は全方式60秒 | 同左 |

マーカーは一辺0.24mの平面白黒パターン、黒枠、方向を識別できる内部4×4パターン。IDと寸法、タスク座標への固定変換だけを既知情報とする。透視投影した実画素をH.264経路へ渡す。検出器は復号輝度画像の閾値処理→連結成分→四角形→内部パターン照合→既知平面とのホモグラフィ姿勢推定とする。既存ライブラリへの依存追加はG1で必要性を判断する。

初期受理条件は最短辺20 pixel以上、四隅が画像内、パターン一致、正の奥行き、再投影RMS 2 pixel以下。複数解は過去の画像推定との整合性で選び、曖昧なら検出失敗とする。真値で解を選ばない。既知マーカーであることをデモにも表示する。遮蔽・圧縮・低照度での検出失敗は隠さない。

### 6.3 共通制御器

追記（G1-06）：以下はG0時点のINITIAL案を保存している。T1の停止位置と壁余裕の共通設定は実測を受けて変更した。現在の値と理由は[G1-06検証説明](Reach_RT_G1_Closed_Loop.md)を参照する。タスクの成功条件・18初期姿勢・物理特性は変更していない。

初期は次の固定状態機械とする。

1. `OBSERVE`：有効な受信画像の推定がなければ停止指令。
2. `APPROACH`：画像推定から目標との距離ρ、目標方向との差αを計算。`ω=clip(1.5α, ±0.8)`、`v=min(0.30, 0.5ρ) × max(0, cos α)`。|α|>30度ならv=0で旋回。加減速制約はロボット側にも適用する。
3. `ALIGN`：ρ≤0.08mで並進を止め、`ω=clip(1.5 × wrap(目標yaw−推定yaw), ±0.8)`。画像上の位置誤差が0.10mを超えたらAPPROACHへ戻る。
4. `HOLD`：位置≤0.08m、yaw≤3度、画像履歴からの推定速度≤0.02m/sなら停止を継続。推定上の完了と真値評価の成功は別イベント。

これは動作未確認の初期制御則である。理想通信の全18初期姿勢を確認し、必要な修正は全方式共通で実施する。T1では既知の通路形状と画像から推定した姿勢から壁余裕を求める。横方向の推定誤差を差し引いた壁余裕が0.05m未満なら並進停止し、向き修正を優先する。回復できない停止は成功にしない。

制動距離には`v²/(2 × 0.60)`と指令が届くまでの移動分を含める。推定誤差は画像の較正実験で得る初期誤差に、画像の年齢と速度・加速度上限による増加分を加える。確率的な安全保証とは呼ばない。G1で理想条件の制御成立と誤差較正を終えるまで数値的な「安全性」を主張しない。

通常画像期限200ms、指令有効期間100ms、ウォッチドッグ250ms。期限は生成時刻からの絶対期限として共通単調時計で判定し、届いてから寿命を延長しない。通信断の際も最大制動0.60m/s²で止め、瞬時停止にしない。

### 6.4 真値と情報の境界

| モジュール | 受け取ってよい情報 | 禁止する入力 |
|---|---|---|
| 物理/描画 | 真の姿勢、壁、照明、適用済み指令 | なし。ただし制御に真値を返すAPIを公開しない |
| 評価器 | 真値、各イベントの読み取り専用コピー | 評価結果から実行中の判断への戻り経路 |
| 認識/制御 | 復号画素、照合済み撮影メタデータ、既知較正/マーカー/目標、過去指令 | 真の現在姿勢、真の壁距離、シミュレータの可視性判定 |
| 送信スケジューラ | 手元AU、送信履歴、到着済み通知、方式ごとに許可した特徴 | 未来の障害、未到着通知、共有メモリ上の受信状態、真値 |
| 画面 | 評価用俯瞰と受信画像を別枠表示 | 俯瞰を制御入力として再利用 |

G1でインターフェースを型として分離し、G2で遅延通知を試験する。データが同じプロセス内にあることを理由に通知経路を省略しない。
